How to confirm you are on THIS build:
  The login screen shows "VeggieConnect · Build v4.12 (...) · server v4.12" at the bottom.
  BOTH numbers MUST say v4.12. If they differ (or a red VERSION MISMATCH banner
  appears), the RUNNING server process is an older build:
  fully stop the app (Ctrl+C / close the terminal), start it again, and
  hard-refresh the browser (Ctrl+Shift+R).
  If you do NOT see that tag at all, you are running an older extraction —
  replace your whole code folder with this zip and restart the app.

Important: when extracting, do NOT mix with an old copy.
  1. Close the running app (Ctrl+C). The server MUST be restarted after every
     extraction — a running `tsx server.ts` process does NOT load new code
     from files extracted later (only the browser pages refresh from disk,
     which is exactly why the Valid Government ID kept showing "Missing"
     while everything else looked up to date).
  2. Delete or rename your previous VeggieConnect3_2/3_3/3_4 code folder.
  3. Extract THIS zip into a fresh folder.
  4. `bun install` then `bun run dev` (or `npm install` / `npm run dev` —
     if npm complains about peer dependencies use: npm install --legacy-peer-deps).
     `npm run dev` now uses `tsx watch`, so future code updates restart the
     server automatically.
  5. Hard refresh the browser (Ctrl+Shift+R).

LEGACY BUILD NOTES (v4.11) — Partial Fulfillment Choice:

1. PARTIAL FULFILLMENT CHOICE ON BUYER REQUESTS (Admin → Buyer Requests)
   Fulfilling a request whose stock is insufficient used to be a dead end —
   the Fulfil button was blocked with a warning toast. Now:
   • Automatic fulfillment is still BLOCKED when stock cannot cover the
     request (the admin never silently sells short).
   • The admin gets an explicit CHOICE: an "Insufficient Stock" modal opens
     showing, per product, how many kg are available vs requested (FULL /
     PARTIAL / NONE badges).
   • "Fulfil Available" delivers ONLY the available products and charges the
     buyer ONLY for them — never the full transaction amount. The shortfall
     is recorded as a refund on the order: credited to the buyer's
     VeggieConnect Pay wallet when the order was already paid, dropped from
     the bill when it was not. Fully-unavailable lines become "Unavailable"
     rulings; partially-covered lines keep their fixed buyer price and carry
     a shortfall note ("6 of 10 kg fulfilled").
   • "Cancel — Source More Stock" backs out so the admin can buy more from
     farmers (Build v4.10 puts those kilograms straight into the Stocks
     menu) and fulfil in full afterwards.
   • The buyer sees the same facts: a shortfall badge on the order line
     ("4 of 10 kg fulfilled • ₱264.00 returned"), a receipt line for the
     returned amount, and the order note explains the partial fulfillment.
   Verified: a paid 10 kg request (₱440) with only 4 kg left fulfils
   partially — warehouse deducts exactly 4 kg, the buyer owes ₱176
   (4 × ₱44), ₱264 is recorded as refunded/credited, and the sourcing
   engine allocates the adjusted 4 kg only.

2. RENAMED "Mark Unavailable & Return Amount" → "Mark Unavailable"
   (Admin → Buyer Requests). Same behavior: the line's amount is returned
   to the buyer's wallet when paid / removed from the bill when unpaid, and
   the order continues with the remaining products. The button tooltip keeps
   the full explanation.

LEGACY BUILD NOTES (v4.10) — Procurement Lands in Stocks:

FIXED — STOCK BOUGHT FROM A FARMER NOW LANDS IN THE STOCKS MENU (EVEN WITH AN
ACTIVE BUYER TRANSACTION OPEN)
  The bug: the quantity the admin bought from a farmer did not ADD to the
  Stocks menu while an active transaction between the admin and a buyer user
  existed.

  Three defects were found and fixed:
  1. DOUBLE DEDUCTION → SKIPPED STOCKING. The buy desk wrote the farmer's
     remaining stock to the backend BEFORE posting the procurement order;
     the backend engine then deducted the same farmer lot AGAIN. When the
     desk bought the WHOLE listing, the lot read 0 by the time the engine
     ran — its allocation came back empty and it early-returned, skipping
     the warehouse stocking step entirely. The bought kilograms never
     reached the Stocks menu. Now: the desk no longer writes stock at all
     (the backend engine is the single writer — deducted exactly once), and
     the engine stocks the warehouse for EVERY committed purchase, even
     when the farmer lot was already empty.
  2. FLAG LOSS → DOUBLE-STOCKED SHELF ON DELIVERY. Orders fulfilled the
     moment they were posted (the desk posts them as 'confirmed') never got
     their exactly-once warehouseStockAdded flag pinned — the order was not
     in the ledger yet when the engine pinned it. A later "Confirm Delivery"
     then added the SAME kilograms a second time. Now the order row is
     written to the ledger BEFORE fulfillment runs, so the flag always
     lands and delivery confirm can never double-add.
  3. AUDIT TRAIL. The farmer listing's boughtQuantity (how much the admin
     has bought from that farmer in total) is now written by the same
     single-writer engine, so it can never double-count either.

  Verified: partial buy (20 of 30 → lot 10, warehouse +20), whole-listing
  buy (15 of 15 → lot 0, warehouse +15 immediately), legacy pre-deducted
  race path (warehouse still +25), delivery confirm adds nothing more, the
  buyer's active transaction is untouched, and farmer lots never go
  negative.

LEGACY BUILD NOTES (v4.9):


FIXED — RE-LISTING THE SAME CROP MERGES INTO ONE CARD (NO DUPLICATES)
  The bug: when a farmer listed the same product again (e.g. Calamansi), a
  SECOND card appeared — in the farmer's My Crops section AND in the admin's
  Crops section.

  The fix:
  • The server now merges a farmer's re-listing into their existing listing
    when it is the SAME farmer, the same crop (name matched loosely, so
    "Okra" merges with "Okra (Lady Finger)") and the same unit. The merged
    card keeps the original record's id (so orders referencing it stay
    valid), takes the NEW price, and SUMS the stock (30 kg + 20 kg = 50 kg).
    Rating and review count survive the merge.
  • Deliberately NOT merged (they stay separate cards): a different farmer's
    same crop, a different unit ("kg" vs "bundle"), a different crop, and the
    supermarket's own warehouse records (those already merged separately).
  • The farmer app now reconciles the server's response by record id after
    posting (replacing the optimistic temporary card) — so My Crops shows
    exactly one card immediately, and the admin's Crops section receives the
    same single merged record from the backend.

LEGACY BUILD NOTES (v4.8):


FIXED 1 — BUYING FROM A FARMER NOW REALLY ADDS THE KILOGRAMS TO THE STOCKS MENU
  The bug: the admin had 30 kg Calamansi in the Stocks menu, bought 30 kg more
  from a farmer — and the Stocks menu still showed 30 kg. Two engine bugs
  combined into a zero-sum shuffle:
  • The admin's own purchase was fulfilled by the BUYER-order sourcing engine,
    which sources WAREHOUSE-FIRST — so it deducted the admin's OWN 30 kg shelf
    stock instead of the farmer's harvest, and the delivery step put the same
    30 kg back. Net result: nothing changed, and the farmer's sold lot was
    never consumed (30 kg invented out of thin air in the totals).
  • The "stock added" exactly-once flag was set on a SHALLOW COPY of the
    order, so it never stuck — every trigger (delivery confirm, server
    restart backfill) added the same kilograms AGAIN (triple-stocked shelves).

  The fix — procurement orders (admin buying from farmers) now have their own
  fulfillment path:
  • The farmer's lot is deducted the moment the order leaves 'pending' (the
    farmer confirms the admin's purchase — the sale is committed).
  • The bought kilograms join the central warehouse stock IMMEDIATELY at that
    same moment: 30 kg in Stocks + buy 30 kg → Stocks shows 60 kg right away.
    The transport chain ("Confirm Delivery & Stock Received in Supermarket")
    stays as the visual delivery step but can no longer be the only moment
    stock arrives — and its stock-add is now a no-op (no double add).
  • The exactly-once flags are pinned on the REAL order row, so re-completing
    the order, re-confirming the haul or restarting the server never re-adds.
  • Cancelling a fulfilled procurement reverses BOTH moves exactly once: the
    farmer's kilograms return to their lot and the warehouse addition is
    subtracted back out (clamped at zero if already resold).

FIXED 2 — FARMER SALES ONLY COUNT TRANSACTIONS THE ADMIN ACTUALLY COMPLETED
  The farmer's Orders-tab date summary ("Total Sales — All Dates / a date")
  counted every non-cancelled transaction, including requests the admin had
  not bought or completed yet. The headline figure now counts ONLY completed
  transactions, matching the Farmer dashboard's Total Sales. The in-progress
  peso value stays visible as an informational line ("In Progress ₱… not yet
  sales — admin has not completed the buy"), so no information is lost.

ALSO SWEPT IN THIS BUILD (transaction integrity between all users)
  • The transport-haul delivery sync and any procurement order that arrives
    already past 'pending' now run the same correct fulfillment dispatcher.
  • Buyer-order behavior is unchanged and re-verified: request ceiling is the
    combined crop availability, nothing is deducted at submission, fulfillment
    deducts warehouse-first then farmer lots, cancellation restocks exactly
    what was taken.

LEGACY BUILD NOTES (v4.6):


1. FIXED — SUBMITTING A PURCHASE REQUEST NO LONGER DEDUCTS FARMER STOCK
   The bug: the moment a buyer submitted a purchase request from the Market
   cart, the farmer's product quantity was deducted — even though the Admin
   had not confirmed anything. (The market cart carried a farmer listing id,

   • Cancelling a STILL-PENDING request returns nothing (no kilo was ever
     taken); cancelling a FULFILLED order still returns every kilo to the
     exact farmer lot / warehouse shelf it came from.
   • Availability checks (overselling guard) still run at submission — a
     request above the combined market stock is still refused.

2. BUYER CANCEL FLOW CLEANED UP (buyer is just a buyer)
   • The confirmation modal is now titled "Cancel Order" (was "Cancel Order
     & Restock") and the "Automatic Inventory Restock — cancelling this order
     immediately returns all reserved kilograms back to the supermarket live
     inventory" explainer box (per-item +N kg breakdown and "Total Restocked"
     line) is REMOVED.
   • The red "Confirm Cancellation & Restock Stock" button now just says

LEGACY BUILD NOTES (v4.4):

DA SUGGESTED DIRECT PRICE IS NOW THE FLOOR FOR FARMER ASKING PRICES
  A farmer can no longer set "Your Farm-gate Asking Price (₱ per kg)" below
  the DA Suggested Direct price of the crop. Example from the request: Banana
  (Lakatan) has a DA Suggested Direct price of ₱55/kg, so the minimum the
  farmer can enter is ₱55 — in the "List Vegetable for Sale" form AND when
  updating an existing product's price in "Edit Vegetable Listing".

  How it works for the farmer:
  • Typing a price below the floor turns the price field red and shows an
    inline message, e.g. "Minimum ₱55.00/kg — the DA Suggested Direct price
    for Banana (Lakatan). Your asking price cannot go below it."
  • The List / Save button refuses to submit while the price is below the
    floor. The DA guide card and the "Use Price" shortcut stay available.
  • Crops the DA bulletin does not cover have no floor (any price allowed).
  • A listing that was ALREADY below the floor before this build keeps its
    stored price while untouched (other fields stay editable); the farmer
    just cannot enter a NEW lower price, and any new input must reach the
    floor or higher.

  Enforced in three places, so it cannot be bypassed:
  1. The farmer's form (live red field + blocked submit),
  2. The server's product UPDATE endpoint — lowering below the floor is
     rejected with a "DA price floor" error (raising to/above the floor is
     always allowed; the "Match DA" button sends exactly the floor),
  3. The server's product CREATE endpoint — a new listing below the floor is
     rejected. Supermarket-owned warehouse stock is exempt (its retail price
     is not a farmer asking price). The floor uses the exact same DA matcher
     the farmer's form shows, so rule and display can never disagree.

  Root cause of both issues: the admin's Crops ▸ Farmer Offers (Buy Desk)

   Every price change the farmer makes (Edit Vegetable Listing, or the

   server memory and the MySQL database, in one atomic update. The admin's
   Crops ▸ Farmer Offers list, the Buy Desk procurement modal, sourcing cost
   computations and analytics now read the farmer's CURRENT price (falling
   back to the legacy field only for old rows). Supermarket-owned warehouse
   stock keeps its original procurement cost — farmer edits never touch it.
   Existing listings whose price was edited before this build also display

2. MINIMUM ORDER UPDATED: 60 KG TOTAL *AND* 20 KG PER PRODUCT
   A buyer order must satisfy BOTH rules (Cart checkout AND the
   "Request Crops" modal enforce the same gates):
   - TOTAL: the kg of every product are added together and the combined
     total must reach AT LEAST 60 kg (e.g. 40 kg Okra + 20 kg Tomatoes
     = 60 kg). Buying more than one product is fine.
   - PER PRODUCT: every product line must be AT LEAST 20 kg on its own
     (e.g. 60 kg of a single product is valid; 10 kg Okra + 50 kg
     Tomatoes is NOT, because Okra is below 20 kg).
   How it is enforced:
   - Market cards: "Add to Cart" is disabled for products stocked with
     less than 20 kg (hover explains "Needs at least 20 kg per product").
   - Tapping "Add to Cart" stages 20 kg of the product (the per-product
     minimum) — the buyer then adjusts upward.
   - Product detail modal: the stepper starts at 20 kg and cannot go
     below it; a note shows "Min 20 kg per product / Total order min 60 kg".
   - Cart: the minus button cannot go below 20 kg (use the new trash
     button to remove a product line entirely). A warning lists every
     product below 20 kg; the submit button says "Each product needs
     20 kg or more" when violated, or "Need X more kg to submit" when
     the 60 kg total is not yet reached.
   - Request Crops modal: the quantity picker starts at 20 kg and cannot
     go below; the same per-product warning + 60 kg total progress bar
     gate the submit button.
